## 1. 三条硬纪律

### ① 装配前后各算一次指纹，且必须贴进提交说明

每次打包（生成 `solution/` 快照或提交 zip）**前后各跑一次**，把 md5 + 行数记进提交说明或改动记录：

```bash
md5sum solution/skills/cor-career/SKILL.md solution/skills/cor-window/SKILL.md solution/manifest.json
wc -l  solution/skills/cor-career/SKILL.md solution/skills/cor-window/SKILL.md
```

🚫 **禁止"凭记忆"声称装的是哪个版本。** 版本号只有一个来源 = 磁盘上的 md5。

### ② 所有正文副本必须同源，改一处即全量同步

`solution/skills/cor-career/SKILL.md` 在库内至少存在以下几份副本，**任何一次改动后必须全部对齐 md5**：

| 副本 | 用途 |
|---|---|
| `solution/skills/cor-career/SKILL.md` | **真源**（引擎实读） |
| `teammate_package/skills/cor-career/SKILL.md` | 队友/装配用副本 |
| `_bak_YYYYMMDD_vXX/` | 上线前备份 |
| 引擎实例目录下的同名文件 | 预览副本（C 盘等） |
| `manifest.json` 的 `instruction`（若内联正文） | 装配真源 |

🚫 **禁止只改一份。** 历史事故：`_verify8.py` 末尾的 `synced n/n` 这一项就是为此设的守卫 —— 它是"副本一致性"的唯一机器检查，**必须保持全绿（当前 `synced 12/12`）**。

### ③ 版本号必须内嵌在正文可搜索处

正文里要能 **grep 到当前版本号**（如 `v57`），且**上一个版本的标记要清理干净**：
- ✅ 保留：`（v57 新增 …）`、`§2.3c 未知分支路由门（v55 新增 …）`
- 🚫 清理：已废弃条目的旧版本标注、指向不存在章节的悬挂引用

**自检命令**（改完后跑，输出应为 0 行）：
```bash
grep -n "指向已不存在章节\|TODO\|FIXME\|待补" solution/skills/cor-career/SKILL.md
```

## 2. 上下文压缩这件事，我们的立场

队友 (2) 的假设是「模型侧压缩上下文导致理解不准确」，所以他**把全文塞进 instruction** 对抗压缩。

**我们的判断**：
- **现象成立** —— 长跑中 agent 确实会"忘掉"或"读歪"早期加载的内容（我们自己的 v51 批实测：`附录G` 字样出现 **0 次**，写了却没人查）。
- **他的解法方向对、但有代价** —— 245 KB 的 instruction 每轮都要吃进上下文预算，反而可能挤掉别的信息；且它**放大的是"过时正文"的危害**（见上文事故）。
- **我们的解法不同** —— 不靠"全文塞满"，靠**把关键纪律做成每手必填的字段**（`M:` 查表状态、`CAP-SNAP` 痕迹行）。
  ⇒ **强制自报 > 重复灌输**。字段不填就是违规，比"文档里写了但没人执行"强得多（v55 融合 1/2 的立法理由）。

---

## 3. 一句话

> **打包不是复制文件，是一次版本对齐操作。**
> 交出去之前，grep 一次版本号、比一次 md5、跑一次 `_verify8.py`（须 `synced` 全绿，当前 `12/12`）。
> 三样任缺其一 ⇒ 不许交。
