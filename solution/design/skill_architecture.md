### 2.1 对"多跑 token"担忧的裁决

之前担心"多个 skill 全部注入 context → 拆分反而更贵"。**源码证明这个担心不成立**：系统提示只放名字，正文靠 Agent 主动加载。
因此拆分的 token 账在**单次注入层面**是净省（主 skill 变小 → 每次加载进上下文后、后续每轮都重复计入的内容变少）。
⚠️ **但实测反证了"总账会省"**：附录外置后（主文件 −37%），play43 的 input/月 反而升至全程最高（1.144M）——
因为按需加载 ≠ 不加载，附录一旦被读进上下文同样逐轮累积。详见 `token_analysis.md` 结论 2 第 2 点。

### 5.2 为什么拆 2 个、而不是官方的 3 个（一次有意识的取舍）

官方 `quickstart.html` 推荐三分（读状态 / 策略判断 / 风险盯防），本方案**没有把附录再拆成第三个 skill**，理由是可验证的风险控制：

1. **历史 transcript 的读取方式已固定**：play43 里 Agent 读附录用的是**裸文件名**（`Let me read appendix-c-high-o.md.`）。
   附录一旦挪到 `cor-appendix/references/`，就多出一层跨 skill 路径解析的不确定性；留在 `cor-career/references/` 则**与已验证通过的路径完全一致**。
2. **依赖方向必须单向**：`cor-window` **不重定义**目标维——凡遇「目标维 / μ / 门槛维」一律回主技能 §2.2c 现算。这样两技能之间只有"调用"没有"循环依赖"。
3. **底线不依赖加载**：§3 红线（R≥1 排雷 / H≤3 回血 / D 跌破门槛补 D）与 cap 表**常驻主技能**，所以**即便 Agent 漏加载 `cor-window`，底线也照样生效**——把"漏加载"的后果限制在"资源调度次优"，而不是"踩雷"。

### 5.3 防漏加载的三重保险

1. `manifest.json` 的 `instruction`（**每次调用都注入、压缩后仍存活**）里点名两个 skill 与 **5 条加载时机**；
2. 主技能 §1 决策流程第 3 条写明"季度体力/主行动 → **cor-window §4**"，§3/§5.1/§5.1b 里的跨技能引用一律显式写成 `cor-window §x`；
3. `cor-window` 的 `description` 自带 5 条触发条件（框架按名清单暴露，description 是 Agent 判断是否加载的依据），并在正文开头用一段"分工声明"写清依赖方向。

**另加一条兜底**：主技能在 §4 / §5.2–§5.4 / §6 的原位置各留一个**指针块**，内含"最小兜底规则"（例如 §4 位置写明 `R≥1 → defuse 占 2E`；`R=0` 时按 §2.2c 目标维对位 1E/2E 动作）。**即使 Agent 完全不去加载 `cor-window`，也不会出现"不知道季度该做什么"的空转**。

### 7.3 为什么「章节号与交叉引用零改动」

搬走的是**正文**，**每一节的标题行都留在 SKILL.md 原位**（正文位置换成一行 `> 📦 **本节正文已外置** → references/ref-*.md` 指针）。因此：

- 全库 221 处「§X」引用（正文内互相引用、`manifest.json` instruction、`design/` 文档）**全部照旧解析** —— 标题还在原文件；
- SKILL.md 顶部新增**「外置章节映射」表**（章节 → ref 文件），Agent 读到「§X」时按表取正文；
- `_verify8.py` 把 12 份 `ref-*.md` **并入 marker 扫描范围**（否则搬走的锚点会被误判成 MISSING），并同步修正 2.4d 表格检查、邻域 / 顺序守卫的文本源。

### 7.4 零改动验证（独立脚本，不依赖搬运脚本自证）

`_skill_split_verify.py` 对比「分层前备份」与「现网（SKILL.md + 全部 ref）」的**行多重集**：原文每一行必须在现网中找到**完全相同的字节行**，且计数不减少 ⇒ 证明内容**未被改写、未被丢失**（判定：✅ PASS）。`_verify8.py` 的 **450 条生效守卫全绿**、`synced` 全 MATCH 作为第二重机器检查。

### 7.5 边界与未验证项

- **只改加载结构，不改任何策略数值**：所有增减值、门槛、公式、判定顺序一字未动（行多重集证明）。
- **本版尚未跑付费局**：常驻载荷下降 56.6% 是**静态事实**；它是否转化为单局 token 下降，仍需真实对局验证（`token_analysis.md` 结论 2 已诚实披露「外置 ≠ 总量下降」——按需加载的内容一旦被读进上下文同样逐轮累积）。
- **风险**：Agent 是否真的按指针行去读 `references/ref-*.md`。对冲手段与附录外置同款（路由表 + 指针行 + instruction 常驻契约 + 未查表兜底）。

## 8. 三层 agent 策略架构（L1 人格 / L2 管理 / L3 数学）—— 设计对齐（2026-09-30）

> 本节回答「策略应该按什么结构组织」。**只做设计对齐**：包内 `skills/` 与 `manifest.json` 一字未改；L1/L2 的落地（qe14）另立。

### 8.0 先定载体：参赛者改不了 `IDENTITY.md`（源码级）

这一条**先于**分层设计，因为它决定每层该往哪写：

| 事实 | 出处 |
|---|---|
| `IDENTITY.md` 由 runner 用模板 `prompts/identity.md` 渲染，**只有两个插槽**：`{participant_skills}`（技能名清单）与 `{instruction}`（取自 `manifest.json` 的 `instruction`） | `install.py` `_write_identity_md`（本地现版 L150–167） |
| 该内容**每次模型调用都进系统提示**，经 ContextAssembleRail，**压缩后仍存活** | 同上函数 docstring（L152–155） |
| ⇒ **参赛者不能自定义 `IDENTITY.md` 正文**：人格底座（「你是职场模拟器 AI 玩家……取得最高分」）由 runner 固定，我们能加的只有 `instruction` 里的**补充锚** | 模板 `prompts/identity.md` L1–L3 |
| `SKILL.md` 相反：走 `skill_tool` 按需加载，台账实测**在 ~369 行处截断**（**66/141 局**触发，返回行数中位 369） | `design/token_analysis.md` §6 |

⇒ **两条通道的性质完全不同**：

- `IDENTITY.md`（← `instruction`）＝ **抗压缩通道**，但**有长度预算**（越长越挤占，且 s1 实测 10942 字 ≈ 55 分、s2 575 字 ≈ 30 余分、s3 6717 字 ≈ 40 余分 ⇒ **长度与分数同向**，见 `packaging-discipline.md` §5q）。
- `SKILL.md` ＝ **截断风险通道**，容量大但**关键判据可能落在线后被切掉**。

**故本层的设计律是：三层各自的「最小可执行核」都必须写进 `instruction`；`SKILL.md` 只作详细展开。**

### 8.1 三层职责 / 载体 / 权限

| 层 | 职责（只做这一件事） | 载体 | 权限 | 现状 |
|---|---|---|---|---|
| **L1 人格**（抗漂移锚） | 只定「不确定时往哪偏」；**不参与任何数值** | `instruction` 首段（→ `IDENTITY.md` 常驻） | **仅倾向** | **待落**（qe14 只做模型贴名，人格锚顺延） |
| **L2 管理模型**（路由 · 节奏） | 只决定「现在用哪个模型、先看哪一节、先做哪件事」；**不产生数值** | `instruction` 中段 ＋ `cor-career/SKILL.md` 路由表 A/B/C ＋ `cor-window` 调度章节 | **路由** | 主体已在；**优先级闸顺延**（qe14 只做模型贴名） |
| **L3 数学模型**（裁决 · 计分） | 算代价、定取舍、出最终选择 —— **全部分数来源** | `instruction` 主体（9864 字契约）＋ `cor-career/SKILL.md` 前段常驻（§2.2b / §2.2c ①② / §3） | **裁决** | **已就位**（qe14 已给 7 个高频模型贴名） |

设计意图：**越往下越硬、越往下越有权**。L1 提供稳定性，L2 提供顺序，L3 提供唯一裁决。

### 8.2 冲突顺序

**`L3 ＞ L2 ＞ L1`** —— 数值裁决压倒路由偏好，路由偏好压倒人格倾向。

> 🔴 **L1 的唯一真实风险**：若把人格写成「角色故事」（如「我是勇于挑战的职场精英」），它会直接与 §3 红线（`R≥1` 排雷、带风险意象的选项一律不选、`high_intensity_work` 永不选）**对撞** ⇒ 人格层从「抗漂移」变成「主动误判」。这与「附录 F 硬编码事件名在 Test 上主动误判」是同一类错误（见 `decision_report.md`）。

### 8.3 模型台账（核心 —— 全文见 `design/model_ledger.md`）

三层里「数学模型层」最容易做错：把它理解成**再往策略里塞新公式**。实际相反 —— **现网 18 条模型里 15 条已经实现、只是没有名字**：

| 状态 | 条数 | 具体是哪些 |
|---|---:|---|
| 已实现 · **无名** | **15** | TOC 识别瓶颈 / 理论产能 `cap` / 有效产能 `eff` / 木桶 perf / 安全库存 SS / (s,S) 再订货 / (R,S) 周期补货 / CCPM 缓冲溢价 / RCCP 可行性闸 / VaR 破产约束 / 鲁棒 minimax / CPM 关键路径 / Stage-Gate / 加权评分 `argmax` / OODA ＋ BSC |
| 半实现 | 1 | 指数平滑 λ —— 只有向导值 `λ_S≈+2.04 / λ_N≈+0.57 / λ_O≈+0.26` |
| **形式未写出** | 2 | 背包 / 约束优化（3E 分配）· 最优停止（W−1 末手） |

**为什么贴名能减少漂移**：模型名是一个**压缩的调用指令**。没有名字时，agent 遇到门槛维要从「门槛 / `cap` / `eff` / 安全垫 / 率*」重推一遍该投谁；有名字时直接调「(s,S) 再订货点：余量 ≤0 就补」——同一结论，**推导步数从 5 步降到 1 步**，出错面随之缩小。

按调用频率把 18 条压成四档（agent 不必记住 18 个模型，只需知道「现在是什么时刻」）：

| 频率 | 调用的模型 |
|---|---|
| **每回合** | OODA 决策循环 · TOC 识别瓶颈（目标维）· `argmax` 加权总账 · 木桶 perf 短板 · 鲁棒 minimax（R 不可见） |
| **每季度** | 背包分配 3E · (s,S) 再订货（门槛维余量 ≤0 强制投）· (R,S) 周期补货 · RCCP 可行性闸 |
| **每窗口** | Stage-Gate 阶段门 · CPM 关键路径（**M18 = 关键活动**）· CCPM 缓冲溢价 · 指数平滑 λ |
| **全程** | VaR ＋ 破产约束 · 最优停止（W−1 末手） |

> 📄 **台账全文**（18 条逐条给出「具体模型 / 数学形式 / 管辖的游戏量 / 落地位置」，另含 5 条缺口的补法）见 `design/model_ledger.md`。

### 8.4 人格层 = 模型使用者的职业操守

人格不写角色故事，写**纪律**。三条，每条挂在一个已存在的评分机制上：

| # | 纪律 | 挂靠的机制 |
|---|---|---|
| ① | **先调模型再听叙事** —— 模型出结果就执行，不用「现实更合理」推翻 | §2.3c `MATCH: EXACT` ⇒ 语义分析一律 OFF |
| ② | **模型输入缺失就用保守值** —— R 按最坏（`R+1`）、未收录按门槛维 `−1` | §2.3b 未收录兜底 |
| ③ | **每步留痕 CAP-SNAP**（六数 ＋ 目标维 ＋ 选项号） | §2.2c ③ 防幻觉 |

全部是**禁令 / 纪律**，与 §3 红线同向 ⇒ 不会产生与 `argmax` 冲突的动作偏好。
🔴 **反例（必须避免的写法）**：写成「我是勇于挑战的职场精英」⇒ 与 §3 红线（`R≥1` 排雷、带风险意象的选项一律不选、`high_intensity_work` 永不选）**对撞** ⇒ 人格从「抗漂移」变成「主动误判」。
