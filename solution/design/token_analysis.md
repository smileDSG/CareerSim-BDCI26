## 3. 三条结论

### 结论 1：token 投入与成绩**无正相关**——多想 ≠ 高分

| 相关性（n=34） | 系数 |
|---|---:|
| corr(input tokens, 终局分) | **−0.434** |
| corr(output tokens, 终局分) | **−0.513** |

补入 play43（n=32→33）后再补入 play44（n=33→34），相关系数由 −0.147 / −0.171 一路走负至 **−0.434 / −0.513**。同代（引擎 1.0.1，play39–play44）对照最直观：

| 局 | 分数 | input 总量 | input/月 | 说明 |
|---|---:|---:|---:|---|
| play40 `0918T085520` | **75.96** | 47.6M | 0.992M | 同代跑满局中**分数最高** |
| play41 `0918T110546` | 71.53 | 43.3M | 0.903M | 同代跑满局中 input 最少 |
| play42 `0918T134737` | 71.00 | 48.6M | 1.013M | 次高 token/月 → 次低分 |
| **play43 `0919T043622`** | **62.12** | **54.9M** | **1.144M** | **token 最高、分数最低**（四局极值同点） |
| play44 `0919T073903` | 67.41 | 52.7M | 1.099M | token/月 次高 → **分数次低**（次高投入 = 次低回报） |
| play39 `0918T073618` | 29.31 | 21.0M | 0.876M | 24 月淘汰（token 总量随之中断，不可比） |

**同代跑满局里，token/月 最高的两局（play43 1.144M、play44 1.099M）恰好是分数最低的两局（62.12 / 67.41）**；token/月 最低的 play41（0.903M）分数反而高于 play42/play44。play43 尤其干净：它同时是**同代 token 之最**与**同代分数之最末**；play44 用第二高的投入换第二低的分，把「多想 ≠ 高分」从单点证据变成了 5 局里的稳定模式。

**这条数据是本方案方法论的根**：既然"让 Agent 多推理"换不来分数，那么提分的唯一杠杆就是把**正确的领域知识前置注入**（SKILL 正文 + `references/`），而不是靠推理时的搜索与试错。SKILL 从 707 行长到 1007 行、再经附录外置（636 行）与双技能拆分（主 + 配套 = 966 行，第二十一轮含「自走率外推 + 冻结闸」），v61 起进一步做**层内物理分层**（主技能常驻 **765 行**、配套 **34 行**，触发层 / 按需层正文外置到 12 份 `references/ref-*.md`），本质上是在用「一次性的知识注入成本」替代「每局反复的推理成本」。

### 结论 2：单局 token 由「局时长 × 单月节奏」驱动，不由"想多久"驱动

input / 存活月 的实测分布非常稳定：均值 **0.773M / 月**、中位 **0.714M / 月**。早淘汰局直接印证——`0918T041511`（38 月）0.836M/月 × 38 ≈ 39.7M，`0917T040632`（8 月）4.3M 总额。

按 SKILL 代际分组看单月成本（**注意：跨引擎代际只比成本、不比分数**）：

| 分组（SKILL 代际） | n | input/月 | 平均分数 |
|---|---:|---:|---:|
| 8 月–9/5 组（附录内联，SKILL ≈707–811 行） | 25 | 0.703M | 76.72 |
| 9/17–9/18 组（附录内联→外置，SKILL 929→1007 行） | 7 | **0.969M** | 77.03 |
| 9/19 组（附录外置 + 双技能拆分，主 SKILL 636→769 行） | 2 | **1.121M** | 64.77 |

两点必须诚实说明：

1. **正文膨胀与单月成本同向**：8 月组 → 9/17–9/18 组，SKILL 正文 +40%，input/月 **+33%**（0.703M → 0.969M），而分数基本持平（76.72 → 77.03）。这是"知识注入边际收益递减"的直接证据。
2. **但"外置省 token"的预期并未兑现**：9/19 组主 SKILL 正文只有 636–769 行（拆分后主+窗合计 ≈966 行），input/月 却**升至 1.121M（全程最高）**。可确认的事实是**外置没有带来总量下降**——原因有三：① 附录并没有消失，只是从"每次都注入"变成"按需加载"（`references/appendix-*.md` 一旦被读进上下文，同样逐轮累积）；② play43/play44 都是 B 级局（L4/L5、多次挂窗），窗口反复重排本身消耗更多回合；③ play44 的账本审计显示 agent 在 §2.5 cap 比对上写了大量逐月核验笔记（token 花在"反复读状态"而非"一次性注入"）。**三个原因在本样本中不可分离**（n=2 观测），故此处不作因果主张。

### 结论 3：SKILL 正文是单局 input 的最大固定成本 → 支持拆分与附录外置（已部分落地）

- SKILL.md 演化为：707 → 1007 行（附录内联版峰值）→ **636 行（第十六轮附录外置）** → **857 行（第十八轮，新增 §2.2c 三维均衡 + eff 规则）** → 拆为 730 行主技能 + 173 行配套技能（第十九轮双技能拆分）→ **769 行主技能 + 197 行配套技能（第二十一轮，新增「自走率外推 + 冻结闸」§2.2c ②第1.5步与 cor-window §5.4 实测斜率判定）** → v55–v60r 各轮累积至 **1364 行主技能 + 375 行配套技能** → **v61 物理分层：主技能常驻 765 行 + 配套常驻 34 行**（触发层 / 按需层正文外置到 12 份 `references/ref-*.md`；常驻载荷 266,858 → **115,739 B**，↓56.6%）。
- 附录 A–F 现已外置为 `skills/cor-career/references/appendix-{a..f}-*.md`（实测 110 / 59 / 52 / 56 / 25 / 104 = 406 行，后扩到附录 A–H + 附录 G 行号索引）；机制词典 `mechanics.md` 另 142 行 → **整个 skill 包正文合计 4364 行**（主技能常驻 765 + 配套常驻 34 + `cor-career/references/` 3198 + `cor-window/references/` 367），其中**常驻部分只有 799 行 = 18%**（且一次加载完整，不再触发框架截断），其余 **82% 为按需加载项**（v61 物理分层后这个比例由约 40% 进一步压到 18%）。
- 反推调用结构（间接推算，仅作量级参考）：play40 output 356k，按单次输出 ~400 token 估 → 约 890 次调用 / 48 月 ≈ 18.5 次/月；input 47.6M ÷ 890 ≈ **53.5k tokens / 次**。主技能常驻 765 行约 16k tokens（按 857 行 ≈ 18k tokens 线性折算），即 **单次注入约占单轮上下文的 ~30%**；**触发层 / 按需层正文已不在常驻部分**（v61 物理分层），只在命中时按需读入（与附录同机制）；窗口调度正文被拆去 `cor-window`，只在季度/窗口时按需加载。
- **比省钱更重要的收益（已实现）**：外置前 play40 transcript 实测 `The skill content was truncated/offloaded.`——单文件 1007 行在加载时被框架截断，附录可能压根没进上下文。外置后 play43 transcript 中 `read_file` 43 次、`grep` 63 次，**按需加载链路正常工作**。
- **应对保密剧本的收益（已实现）**：Test 剧本保密，附录中 234 条硬编码事件条目在 Test 上可能**完全命中不到**。通用规则（§2.2 判定阶梯 / §2.2c 三维均衡 / §5.4 补缺压力 / §3 红线）已被放到决策链最前，查表降级为"命中才用"的参考。

3. **把知识固化进 SKILL，而不是让 Agent 现场推理**——结论 1 的直接推论。
4. **提交前跑零成本预检**——`python -m career_sim_runner validate --submission solution`（`validate_submission` 只读布局/manifest/frontmatter，不联网、不计费）。

## 5. 已知偏差（诚实声明）

1. 8 月组与 9 月组的分数**不可直接比较**：引擎 1.0.1 的 `stat_clamp` 自 play39（9/18 07:36）起生效，前后是两代机制。上表分组只用于比较"单月 token 成本"这一与引擎无关的量。
2. 相关性系数基于 **n=34** 的粗样本，且 SKILL 迭代与引擎变更在时间上重叠，存在混杂——**引擎换成 1.0.1 后分数整体下移、同时后期局 token 更高，两者会共同推高负相关**。因此本节的相关系数**只用于否定"token 越高性能越好"这一假设**，不足以支持任何因果主张（"少花 token 能提分"同样不被支持）。
3. 结论 3 的调用次数为间接推算（运行时未记录调用数），误差可能较大，故只给出量级（"约占三成半"），不作为精确承诺。
4. `20260827T100522Z` 未记录 token、`20260830T041448Z` / `20260917T103349Z` 无评分结果，三局已从统计中剔除。
5. 9/19 组是 **n=2 观测**（play43/play44）：它们在"SKILL 正文经拆分后最小"的同时"input/月 最高"，二者不可分离，故结论 2 第 2 点只陈述事实、不作因果结论。

## 6. 成本账本实测（v60r-qe9 · 141 局技能加载实算）

> **工具**：`_cost_ledger.py` → `__cost_ledger.txt` / `__cost_ledger.jsonl`。
> **口径**：只读真实对局的 `events-*.jsonl`，从 `tool_result` 里**还原**出被注入模型的正文
> （剥掉包装与 repr 转义）后取 `len()` —— 即**模型实际收到的字符数**（真值，与本地文件版本无关）。
> 分三类：① **触发** = `skill_tool`（返回 `skill_content`）；② **常驻** = `read_file` 读 `SKILL.md`；
> ③ **按需** = `read_file` 读 `references/*.md`。`grep` 只记次数不计字符；失败的读单列「失败」。

### 6.1 总览

| 项 | 值 |
|---|---|
| 对局目录 / 有 events / 有技能加载记录 | 149 / 147 / **141** |
| 技能加载总字符 | **15,556,825**（常驻 **13,596,311 = 87.4%** / 按需 **1,960,514 = 12.6%**）|

⚠️ **诚实边界**：141 局**全部**跑在分层前的代际（0/141 同版本）。故本账本**不是分层后的效果验证**，
而是**分层的依据** —— 它量化了「常驻层占 87.4%」与「截断白付」两个病灶。
分层效果只能在后续对局复测（列为待办，见 §6.5 ⑤）。

### 6.2 常驻层：单局技能成本的主体，且被框架截断

| 项 | 值 |
|---|---|
| `skill_tool` 触发 | 261 次 / **8,193,853 字符**（cor-career 186 次；cor-window 75 次）|
| `SKILL.md` 直读 | 282 次 / **5,402,458 字符**（占常驻 40%）|
| `skill_tool` 返回行数 | min 52 / **中位 369** / max 930 —— 明显小于当时文件行数 ⇒ **常驻层被截断** |
| 同一局既触发又直读 `SKILL.md`（= 为截断白付二次读） | **66 / 141 局** |
| 单局常驻加载次数 | 均值 3.85（min 1 / max 30）|
